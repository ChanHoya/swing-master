# Phase 0 측정 기록 (2026-09-19)

Render 무료 티어(512MB / 0.1 CPU)를 로컬 Docker 로 재현해 실측했다.
공개 노출 없이, 배포 전에 알아야 할 것을 먼저 알아내는 것이 목적이었다.

## 결과

| 항목 | 값 |
|---|---|
| 빌드 성공 | ✅ (`--platform linux/amd64`, `python:3.12-slim`) |
| 이미지 크기 | 1.58GB (Render 한도 10GB) |
| 설치된 opencv | `opencv-python-headless 4.11.0.86` 하나 (GUI: NONE) |
| 분석 결과 | `status: done` — 전 구간 완주 |
| **최대 메모리** | **355.0 MiB / 512 MiB (69%)** |
| OOMKilled | false |
| 분석 소요 시간 | 470.3초 (다운로드 3.3s / 포즈 441.3s / 오버레이·업로드 29s) |
| 판정 | **메모리 통과. 속도는 사용자 판단 필요** |

입력: `골프스윙호야1.mp4` (2.0MB). 로컬 네이티브 기준 같은 파이프라인이 9.5초다.

## 도달하기까지 깨진 것 다섯 가지

모두 Render 빌드 큐에서 했다면 건당 수 분에서 십여 분이 들었을 것들이다.

**1. `mediapipe==0.10.33` 을 찾지 못함**

맥이 arm64 라 Docker 가 arm64 로 빌드하는데, 0.10.33 의 리눅스 휠은
`manylinux_2_28_x86_64` 하나뿐이다. aarch64 용이 없어 pip 이 1.0.x 만 보고
"Could not find a version" 으로 죽는다. 커밋 `03e8504` 가 남긴
"리눅스에는 1.0.0/1.0.1 만 있다" 는 관찰은 **그 환경에서 정확했다.**

Render 는 `linux/amd64` 이미지만 받으므로(공식 문서) 플랫폼을 맞추면 해결된다.
**mediapipe 버전 상향은 필요 없었다.** `Dockerfile` 의 `FROM` 에 고정했다.

**2. numpy 가 소스 빌드로 넘어가 컴파일러를 찾지 못함**

numpy 1.26.4 는 cp313 휠을 내지 않는다(cp39~cp312 까지). `python:3.13-slim` 에는
컴파일러가 없어 실패한다. 로컬 맥의 `.venv` 에 3.13+numpy 1.26.4 가 있는 것은
clang 으로 직접 컴파일됐기 때문이고, 그 상태를 `pip freeze` 한 것이
`requirements.txt` 다. 즉 Dockerfile 주석의 "3.13 에 고정했으니 베이스를 맞춘다"는
전제가 거꾸로였다 — 3.13 이라서 설치가 안 된다.

`python:3.12-slim` 으로 내리니 **버전 핀을 하나도 바꾸지 않고** 전부 휠로 설치됐다.

**3. DB 연결 거부 — `backend/.env` 가 localhost 를 가리킴**

`config.py` 는 `env_file=".env"` 를 프로세스 작업 디렉터리 기준으로 읽는다.
백엔드는 `backend/` 에서 실행하므로 `backend/.env` 를 읽고, 그 값은
`localhost:5432` 다. 루트 `.env` 의 Supabase 주소는 쓰이지 않는다.

**4. Supabase 프로젝트가 소멸**

루트 `.env` 의 Supabase 는 `tenant/user ... not found` 로 응답한다. 프로젝트가
삭제됐다. 즉 "DB 는 이미 클라우드에 있다"는 설계 문서의 전제가 틀렸다.
로컬 Postgres 에 사용자 1명·업로드 25건·분석 25건(완료 24건)이 있고,
이들이 참조하는 R2 객체는 살아 있다.

**5. `libGLESv2.so.2` 없음 — MediaPipe 의 네이티브 의존성**

가장 잡기 어려운 것이었다. `Dockerfile` 이 `libgl1` 만 설치하는데 MediaPipe 의
C 바인딩은 `libGLESv2.so.2` 를 요구한다. `libegl1 libgles2` 를 더해 해결했다.

**이 결함은 헬스체크로 절대 잡히지 않는다.** `import mediapipe` 는 성공하고
앱은 정상 기동하며 `/health` 도 200 을 준다. 네이티브 라이브러리는
`PoseLandmarker.create_from_options()` 가 불리는 **첫 분석 시점**에야
dlopen 되기 때문이다. 그냥 배포했다면 "배포 성공 → 첫 업로드 실패" 를 겪었을 것이다.

## 틀렸던 진단 두 가지 (기록용)

- **"지난 세션의 mediapipe 진단은 오진이다"** — 아니었다. PyPI 에서 x86_64 휠만
  보고 아키텍처를 놓친 것은 이쪽이다. 다만 처방은 달라진다(버전 상향이 아니라 플랫폼).
- **"opencv 중복이 `libGLESv2` 실패의 원인"** — 아니었다. headless 로 강제한 뒤에도
  같은 에러가 났고, 트레이스백은 MediaPipe 를 가리켰다. headless 정리 자체는
  유효했다(이미지 160MB 절감, `03e8504` 의 의도 복원).

## 소요 시간을 어떻게 읽어야 하는가

**470초를 Render 예상치로 그대로 쓰면 안 된다.** 이 측정은 arm64 맥에서 amd64 를
QEMU 에뮬레이션한 것이라 네이티브보다 느리다. 반대로 메모리는 에뮬레이션이
오버헤드를 **더하므로**, 355MB 에 들어갔다면 네이티브에서는 확실히 들어간다.

다만 낙관하기 어렵다. 로컬 네이티브 9.5초가 여러 코어를 쓴 결과라면 대략
40 코어·초 규모이고, 0.1 CPU 에서는 그것만으로 400초 안팎이 나온다. 즉
**에뮬레이션을 걷어내도 0.1 CPU 라는 제약 자체가 지배적**일 가능성이 크다.

정확한 값은 Render 에 올려서 재는 수밖에 없다. 무료이므로 재보는 비용은 시간뿐이다.
