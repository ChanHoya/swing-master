# 브라우저 포즈 추출 설계 (2026-09-20)

포즈 추출을 서버에서 폰으로 옮겨 분석을 수 초대로 줄인다.

## 왜

Render 무료 티어(0.1 CPU)에서 분석이 **94~296초** 걸린다. 로컬 맥북의 같은
파이프라인은 5~6초다. 폰 사용자는 여기에 업로드 시간이 얹힌다.

시간의 93%가 포즈 추출이다. 지표·규칙 계산은 밀리초다. 즉 **MediaPipe 추론
한 가지**가 병목이고, 그것만 폰으로 옮기면 서버가 할 일은 1~2초로 준다.

측정으로 확인한 부수적 사실들도 모두 같은 방향을 가리킨다.

- 서버가 프레임을 640px 로 줄여 넣어 멀리 찍힌 골퍼는 **어깨폭 17px** 이 된다.
  그 크기에서는 복원할 정보가 없다.
- `skip=2` 로 두 프레임에 하나만 추론해 스윙 전체에 측정점이 **30개 남짓**이다.
  점이 성글어 손 궤적의 떨림과 원호 깎임이 절충 관계에 갇혀 있다
  (`docs/superpowers/plans/` 의 궤적 조사 참고).
- 파일이 클수록 프레임당 비용이 0.70초에서 **2.39초**까지 오른다. 원본 해상도
  디코딩 비용이다.

폰에서는 셋 다 사라진다. 원본 해상도로 넘길 수 있고, 프레임을 다 쓸 수 있고,
디코딩이 기기에서 끝난다.

## 사용자 결정

| 항목 | 결정 |
|---|---|
| 영상 | **분석과 분리해 백그라운드 업로드.** 재생 기능을 전부 지킨다 |
| 오버레이 JPEG 7장 | **저장하지 않고 화면에서 캔버스로 그린다** |
| 서버 포즈 파이프라인 | **삭제한다.** 폴백을 두지 않는다 |
| 추출 경로 | **둘 다.** 현장 촬영 실시간 + 갤러리 파일 |

세 번째는 되돌릴 곳을 없애는 결정이므로, 검증 순서에서 삭제를 맨 뒤에 둔다.

## 실현 가능성 확인

`@mediapipe/tasks-vision` 의 `PoseLandmarkerResult` 가 `worldLandmarks` 를
제공한다(공식 저장소 `pose_landmarker_result.ts`). 회전 지표 3종은 미터 단위
3D 없이 계산할 수 없으므로 이것이 전제 조건이었다. `detectForVideo(frame,
timestamp, callback)` 로 영상 모드도 지원하고, 모델 파일은 지금 쓰는
`pose_landmarker_lite.task` 그대로다.

## 1. 전체 구조

| | 지금 | 이후 |
|---|---|---|
| 포즈 추출 | 서버 (Render 0.1 CPU) | **폰** |
| 지표·단계·궤적·규칙 | 서버 | **서버 그대로** |
| 오버레이 | 서버가 JPEG 7장 렌더 | **화면에서 캔버스로** |
| 영상 | 분석의 입력 | **재생용, 백그라운드 업로드** |

`metrics.py`·`phases.detect_phases`·`tracks.py`·`feedback/*` 는 **한 줄도
바뀌지 않는다.** numpy 외 의존성을 두지 않은 제약이 여기서 값을 한다.

알려진 결함 하나가 삭제로 해결된다. AGENTS.md 에 "`detect_swing_window` 가
영상 전체를 반환한다(실패 3/11)"고 적힌 함수가 없어진다. 영상 크롭 구간은
탐지된 단계에서 유도한다 — 어드레스부터 피니시까지 앞뒤 여유. 회색조 차분
휴리스틱보다 정확하다.

## 2. 브라우저 추출 모듈

```
lib/pose/types.ts        서버 스키마와 1:1 대응하는 타입
lib/pose/extractor.ts    프레임 → 좌표. 프레임이 어디서 오는지 모른다
lib/pose/sources.ts      프레임 공급원 둘 (카메라 스트림 / 파일)
lib/pose/swingWindow.ts  좌표 → 스윙 구간. MediaPipe 를 모른다
```

`extractor` 가 공급원을 모르고 `swingWindow` 가 MediaPipe 를 모르는 것이
핵심이다. `swingWindow` 는 순수 함수라 합성 좌표로 검증할 수 있다.

**공급원 둘, 추출기 하나**

| | 카메라 (현장) | 파일 (갤러리·PC) |
|---|---|---|
| 프레임 | `getUserMedia` → `requestVideoFrameCallback` | `<video>` 재생하며 같은 콜백 |
| 녹화 | `MediaRecorder` 가 동시에 기록(재생용) | 이미 파일이 있음 |
| 특이점 | 프레임 유실 계측 필요 | 없음 |

실시간에서는 폰이 버거우면 프레임이 조용히 건너뛰어진다. 기대 프레임 수와
실제 추론 수를 세어 화면에 보여준다("30fps 중 24 인식"). 지어내지 않는다는
원칙에 맞고, 결과가 나쁠 때 원인을 알 수 있다.

**스윙 구간은 포즈로 찾는다.** 손목이 올라갔다 빠르게 내려오는 패턴은 오인할
여지가 거의 없다. 회색조 차분으로 좁히려던 이전 시도는 정상 6/11 → 2/11 로
악화돼 원복됐다. 좌표가 이미 있으니 공짜다.

전부 추론한 뒤 좌표로 구간을 정한다. 300프레임을 넘는 긴 영상에서만 성기게
훑어 구간을 먼저 찾고 그 안을 촘촘히 돌린다 — 짧은 영상에 두 경로를 만들
이유가 없다.

**해상도를 깎지 않는다.** 원본 프레임을 그대로 넘겨 MediaPipe 가 자체 ROI
크롭을 원본 픽셀에서 하게 한다. `skip` 도 없앤다. 측정점이 2배가 되어 같은
잡음 억제를 절반 길이의 창으로 얻는다 — 궤적 떨림의 진짜 해법이다.

**모델은 우리 것을 쓴다.** `pose_landmarker_lite.task`(5.5MB)를
`frontend/public/` 에 두고 WASM 런타임도 npm 패키지에서 자체 호스팅한다.
구글 CDN 을 런타임 의존으로 두지 않고, 지금과 똑같은 모델을 써서 숫자를
비교 가능하게 유지한다.

## 3. 서버 변경

**새 엔드포인트 하나가 기존 세 개를 대체한다.**

```
POST /analysis
  { camera_angle, club, fps, resolution, frames: [{ t, world, xy, vis }] }
→ { analysis_id, overall_score, grade, metrics, feedback }
```

`POST /upload` → `GET /status` 폴링 → `GET /result` 3단계가 동기 호출 하나가
된다. `BackgroundTasks` 도, `queued`/`processing` 상태도 없어진다. 유일하게
느린 Gemini 윤문은 실패해도 규칙 결과가 그대로 나가는 구조이므로 타임아웃을
8초로 조인다.

`xy` 는 0~1 정규화로 받고 서버가 `resolution` 을 곱해 픽셀로 바꾼다.
MediaPipe JS 가 정규화 좌표를 내주므로 변환이 한 곳에 모인다.

**어댑터는 함수 하나뿐이다.**

```python
def sequence_from_payload(payload) -> PoseSequence
```

이것만 새로 쓰면 `compute_metrics`·`detect_phases`·`build_tracks`·`evaluate`
는 그대로 쓴다.

**삭제**: `pose.py`, `overlay.py`, `detect_swing_window`, 그리고 `mediapipe`·
`opencv-python-headless`·`supervision`·`scipy`·`matplotlib` 의존성. Dockerfile
의 `libgl1`·`libegl1`·`libgles2`·`fonts-nanum` 도 함께. 이미지 1.58GB → 약
200MB, 메모리 355MB → 100MB 남짓.

**좌표를 DB 에 저장한다.** `_meta.landmarks` 에 `world` 와 `xy` 를 함께 둔다
(분석당 약 200KB. Neon 무료 0.5GB 에 100건이면 20MB).

이번 작업 중 백필을 두 번 했고, 그때마다 영상 27건을 내려받아 포즈를 다시
추출해야 했다. 좌표가 저장돼 있으면 알고리즘을 고쳐도 영상 없이 즉시
재계산된다. 200KB 로 그것을 산다.

**스키마 변경** — 영상이 분석의 전제가 아니게 된다.

- `analyses` 에 `camera_angle`·`club`·`video_url` 이동/추가
- `analyses.upload_id` 를 nullable 로 완화
- 영상은 나중에 백그라운드로 올라와 `video_url` 을 채운다
- 상세 화면 경로가 `upload_id` → `analysis_id` 기준으로 바뀐다
  (히스토리는 이미 둘 다 반환한다)

## 4. 화면

**촬영 화면** — 이 작업의 핵심 화면. `getUserMedia` 미리보기 위에 녹화 버튼,
녹화 중 **인식 중인 스켈레톤을 겹쳐** 보여준다. 폰이 사람을 잡고 있는지 촬영
전에 알 수 있어야 한다 — 지금은 올리고 몇 분 기다린 뒤에야 인식 실패를 본다.
실제 인식 프레임 수도 함께 표시한다. 정지하면 결과가 1~2초 안에 뜨고, 영상은
그 뒤 백그라운드로 올라간다.

**파일 선택 경로** 는 지금 드롭존을 유지하되 업로드 대신 "좌표 추출 중 45%"
가 돈다.

**분석 상세 화면** 은 단계 카드를 `<img src=overlay_url>` 대신 캔버스에
그린다 — 영상을 해당 단계 시각으로 옮기고 저장된 좌표로 스켈레톤을 얹는다.
손 궤적과 같은 방식이다. 구워진 이미지가 아니므로 켜고 끄고 확대할 수 있다.

**기존 28건 호환**: 옛 기록은 오버레이 JPEG 를 갖고 좌표가 없다. 새 기록은
반대다. 상세 화면이 둘 다 다룬다 — 좌표가 있으면 그리고, 없으면 저장된
이미지를 쓴다. 옛 기록을 버리지도, 가짜 좌표를 만들어 넣지도 않는다.

## 검증 — 순서가 안전장치다

서버 파이프라인을 지우면 되돌릴 곳이 없으므로 삭제를 맨 마지막에 둔다.

| 순서 | 내용 | 통과 기준 |
|---|---|---|
| **1. 스파이크** | 실제 폰에서 MediaPipe 속도 측정 | 8초 영상 좌표 추출 **10초 이내**. 넘으면 멈추고 재논의 |
| **2. 대조** | 같은 영상을 서버 경로와 브라우저 경로로 각각 분석 | 지표 8개가 서로 비슷한가 |
| 3. 새 엔드포인트 | `POST /analysis` + 어댑터 | 기존 201개 + 신규 테스트 통과 |
| 4. 화면 | 촬영·파일·상세 | `npx tsc --noEmit`, 실제 폰 |
| 5. 삭제 | 서버 파이프라인·의존성 | 남은 테스트 186개 통과, 이미지 200MB 확인 |

**1번은 게이트다.** iOS Safari 의 WASM 성능은 미지수이고, 그것이 안 되면 이
설계 전체가 성립하지 않는다. 본 작업 전에 작은 페이지 하나로 먼저 잰다.

**2번이 가장 중요하다.** 브라우저 MediaPipe(WASM)와 서버 MediaPipe(네이티브)가
같은 모델이라도 좌표가 완전히 같지는 않다. 점수가 달라지면 과거 기록과 비교가
깨진다. 차이를 먼저 재고 사용자에게 보고한 뒤 넘어간다. 크게 어긋나면 설계를
다시 본다.

5단계에서 테스트 15개가 함께 사라진다 — `test_pose.py` 5개와
`test_overlay.py` 10개다. 지우는 모듈의 테스트이므로 정상이며, 201 − 15 =
**186개**가 남아야 한다. 그보다 더 줄었다면 무언가를 잘못 지운 것이다.

**한계를 명시한다.** 프론트엔드에는 테스트 프레임워크가 없다(`package.json`
에 test 스크립트 없음). 순수 함수인 `swingWindow` 를 포함해 브라우저 코드는
타입 검사와 실제 기기 확인에 의존한다.
