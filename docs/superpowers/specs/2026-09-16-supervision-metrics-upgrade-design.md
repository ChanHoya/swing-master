# Supervision 기반 지표 실측화 업그레이드 — 설계

- **작성일**: 2026-09-16
- **상태**: 설계 승인 완료, 구현 계획 수립 대기
- **범위**: `backend/app/services/` 전면 재구성 + 프론트엔드 지표 표시 확장
  + 기기 간 흐름(모바일 촬영 → PC 상세 분석, §9)

## 0. 배경 — 이 작업이 시작된 경위와 전제의 정정

이 작업은 **"유료 LLM 비용을 오픈소스로 대체한다"**는 목표로 출발했다.
조사 결과 **그 전제는 사실이 아니었다.**

### 0.1 비용 문제는 존재하지 않았다

- 코드베이스 전체에서 유료 API를 호출하는 지점은
  `backend/app/services/llm_feedback.py` **단 한 곳**이다.
- 그 호출의 요청 본문은 `{"contents": [{"parts": [{"text": prompt}]}]}` 뿐이다.
  **영상도 이미지도 전송하지 않는다.** `inline_data`, 파일 업로드, 드릴 이미지 생성 모두 없다.
- 영상 분석은 100% 서버 내부의 MediaPipe가 로컬로 처리한다. 외부 비용이 발생하지 않는다.
- 호출 1건은 입력 약 600토큰 + 출력 약 800토큰 수준으로, 분석 1건당 몇 원 단위다.
- **사용자가 Google AI Studio 콘솔을 확인한 결과 최근 3개월간 청구 내역이 없었다.**
  체감했던 비용은 별개 서비스(Call2Text)의 것이었다.

→ **오픈소스 전환으로 절감할 비용은 0원이다.** 비용을 근거로 한 작업은 모두 폐기한다.

### 0.2 대신 발견된 진짜 문제

LLM 프롬프트는 7개 지표를 넘기지만, **실제로 측정되는 것은 2개뿐**이다.

| 지표 | 실제 값의 출처 |
|---|---|
| `spine_angle` | 실측 (`pose_estimator.py`) |
| `tempo_ratio` | 실측 |
| `head_movement` | **하드코딩 `1.7`** |
| `hip_rotation` | 미계산 → `metrics.get()` 기본값 `32.0` 고정 |
| `shoulder_rotation` | 미계산 → 기본값 `88.0` 고정 |
| `knee_flex` | 미계산 → 기본값 `22.0` 고정 |
| `weight_transfer` | 미계산 → 기본값 `55.0` 고정 |

**모든 사용자가 5개 지표에 대해 동일한 가짜 숫자를 받고 있다.**
서비스는 사실상 척추각과 템포 두 개만 보고 피드백을 쓰고 있었다.

그런데 그 재료는 이미 있다. MediaPipe `PoseLandmarkerResult`는
`pose_landmarks`(2D 정규화)와 함께 **`pose_world_landmarks`(힙 중심 원점, 미터 단위 3D)**
를 반환하는데, 현재 코드는 후자를 한 번도 사용하지 않는다.

→ **이 업그레이드의 1순위 목표는 가짜 지표 5개의 실측화다.**

## 1. 목표와 비목표

### 목표

1. 가짜 지표 5개를 `pose_world_landmarks` 기반 실측으로 교체한다.
2. X-factor(어깨 회전 − 힙 회전) 지표를 신규 추가한다.
3. supervision으로 오버레이 렌더링을 표준화한다.
4. LLM 장애와 무관하게 동작하는 규칙 기반 피드백 엔진을 만든다.
5. `pose_estimator.py`(439줄, 책임 8개)를 책임 단위로 분할한다.
6. **업로드에 사용자를 귀속시킨다** — 현재 `user_id`가 항상 `NULL`이라
   히스토리가 깨져 있다 (§9.2).
7. **모바일 촬영 → PC 상세 분석의 기기 간 흐름**을 만든다 (§9).

### 비목표 (이번 범위 밖)

- LLM 공급자 교체 — 비용 문제가 없으므로 Gemini를 유지한다.
- 클럽 탐지 / 클럽 헤드 궤적 — 별도 데이터셋 라벨링이 필요하다.
- 7단계 탐지 알고리즘 개선 — 기존 `motion_mag` 휴리스틱을 유지한다.
- 포즈 추정의 클라이언트 이전 — 서버 사이드를 유지하기로 결정했다
  (`AGENTS.md`의 TODO 중 해당 항목은 "서버 유지"로 확정).

### 전제

- **개인 용도이며 외부 서비스화 계획이 없다.** 따라서 Ultralytics의 AGPL-3.0
  라이선스는 제약이 되지 않는다. (배포·네트워크 서비스 제공 시점에 발동하므로,
  향후 서비스화한다면 이 결정을 재검토해야 한다.)

## 2. 아키텍처 — 모델 역할 분담

### 2.1 확인된 제약

| 사실 | 근거 |
|---|---|
| `sv.KeyPoints.xy`는 `(n, m, 2)` — **2D 전용** | supervision 0.30.3 `key_points/core.py` |
| `from_mediapipe()`는 `landmark.x * w, landmark.y * h`만 취하고 **z를 버린다** | 동 소스 |
| YOLO-pose는 COCO 17개 키포인트를 **이미지 평면 2D로만** 회귀한다 | 모델 구조 |
| MediaPipe `pose_world_landmarks`는 **미터 단위 3D**를 준다 | `Landmark` 필드: x, y, z, visibility, presence, name |

→ **어깨 회전·힙 회전·X-factor는 2D로 계산할 수 없다.**
몸이 회전하면 2D 화면상 어깨 폭이 줄어들 뿐 각도가 나오지 않는다.
**이 지표들의 유일한 출처는 MediaPipe `pose_world_landmarks`다.**

### 2.2 역할 분담

```
프레임 → YOLO-pose로 골퍼 탐지 (sv.Detections, 바운딩박스)
       → 박스로 ROI 크롭 (골퍼가 프레임을 꽉 채움)
       → 크롭을 MediaPipe에 투입 → pose_world_landmarks (3D)
       → 3D로 지표 8개 계산
       → supervision Annotator로 오버레이 렌더
```

| 구성 요소 | 역할 | 선정 근거 |
|---|---|---|
| **YOLO-pose** (`yolo11n-pose`) | 골퍼 탐지 + ROI 박스 | 비스듬한 각도·원거리에 강건. `sv.Detections`로 향후 클럽 탐지와 통합 가능 |
| **MediaPipe** (현행 유지) | 크롭 ROI에서 3D 포즈 추출 | 3D world landmark를 주는 유일한 쪽. 33개 랜드마크(발뒤꿈치·발끝 포함) |
| **supervision** 0.30.3 | 키포인트 표준화 + 오버레이 렌더 | MIT 라이선스. `make_overlay`의 cv2 수작업 40줄 대체 |

### 2.3 YOLO가 해결하는 실제 문제

현재 `analyze_swing()`은 **전체 프레임을 640p로 축소해 통째로** MediaPipe에 넣는다.
골퍼가 프레임에서 작게 찍히면 인식이 무너진다. 그 증거가 코드에 남아 있다:

- `min_pose_detection_confidence`를 기본 0.5에서 **0.25로 하향**
- 그래도 실패하면 `"포즈 인식 실패 (감지된 프레임 N개)"` 예외

ROI 크롭을 거치면 골퍼가 입력 프레임을 꽉 채우므로 인식률이 개선된다.

### 2.4 배포 경로 이원화

Ultralytics는 torch를 끌어온다 (**macOS arm64 휠 기준 121MB**, 확인 완료).
개인용 로컬 실행에는 문제없으나 Railway 배포 시 이미지 크기와 콜드스타트가 늘어난다.

- **기본값**: MediaPipe 단독 경로. Railway 배포와 ultralytics 미설치 환경이 여기에 해당한다.
- **로컬 실행**: `.env`에서 `USE_YOLO_ROI=true`로 켠다.

`settings`에 `USE_YOLO_ROI: bool = False`를 두고, `pose.py`가 **플래그가 켜져 있고
ultralytics import에도 성공한 경우에만** YOLO 경로를 쓴다. 둘 중 하나라도 아니면
조용히 MediaPipe 단독으로 내려간다. 무거운 의존성이 배포를 깨뜨리지 않는다.

## 3. 지표 계산 사양

MediaPipe world landmark는 **힙 중심을 원점으로 한 미터 단위 3D 좌표**다.
랜드마크 인덱스는 정규화 좌표와 동일하다
(11/12 어깨, 13/14 팔꿈치, 15/16 손목, 23/24 힙, 25/26 무릎, 27/28 발목, 0 코).

| 지표 | 계산 | 기준 프레임 | 목표값 |
|---|---|---|---|
| `shoulder_rotation` | 어깨 벡터 `P[12]−P[11]`을 수평면(x-z)에 투영 → `atan2(dz, dx)`. 어드레스 대비 탑에서의 각도 차 | 어드레스 → 탑 | ≥ 90° |
| `hip_rotation` | 힙 벡터 `P[24]−P[23]`에 동일 적용 | 어드레스 → 탑 | ≥ 45° |
| `x_factor` 🆕 | `shoulder_rotation − hip_rotation` | 탑 | 40~50° |
| `knee_flex` | 힙–무릎–발목 3점 사이각, 좌우 평균. `180° − 사이각` | 어드레스 | 20~30° |
| `spine_angle` | 어깨 중심 → 힙 중심 벡터의 수직축 대비 전방 기울기 (현행 2D → 3D 교체) | 어드레스 | 30~45° |
| `head_movement` | 코(0)의 최대 변위. **§3.1의 이유로 2D 정규화 좌표를 쓰고, 어깨 너비를 자로 삼아 cm 환산** (성인 어깨폭 ≈ 40cm) | 어드레스 → 임팩트 | ≤ 5cm |
| `tempo_ratio` | `(탑−어드레스) / (임팩트−탑)`, **프레임 인덱스가 아닌 실제 초 단위** | 전 구간 | 3.0 |
| `weight_shift` | §3.3 참조 — **대리 지표**. §3.1의 이유로 2D 픽셀 좌표 사용 | 어드레스 → 임팩트 | 잠정 10~20% (§7 4단계에서 확정) |

### 3.1 `head_movement`와 `weight_shift`만 2D 좌표를 쓰는 이유

`pose_world_landmarks`는 **힙 중심이 원점**이므로 몸 전체의 공간 이동이 상쇄된다.
이 좌표계에서는 다음 두 지표를 계산할 수 없다.

- **`head_movement`**: 코의 변위를 재면 "몸통 대비 머리의 상대 움직임"이 나오는데,
  골프에서 말하는 헤드 무브먼트는 **공간상의 절대 변위**다.
- **`weight_shift`**: 골반 중심이 곧 원점이므로 **x좌표가 항상 0이다.**
  좌우 이동량 자체가 정의상 측정 불가능하다.

따라서 이 둘만 2D 좌표를 쓴다. 단 정규화 좌표(0~1)는 가로·세로 스케일이 달라
거리 계산이 왜곡되므로, **`sv.KeyPoints.from_mediapipe()`가 반환하는 픽셀 좌표**를 쓴다
(이 함수가 `landmark.x * width, landmark.y * height`로 변환해 준다 — §2.1).

- `head_movement`: 어드레스 프레임의 어깨 너비 픽셀 거리를 실제 어깨폭(≈40cm)에
  대응시켜 cm로 환산한다.
- `weight_shift`: 골반 중심 x의 이동 픽셀을 스탠스 폭 픽셀로 나눠 %로 만든다.
  둘 다 픽셀이므로 환산 없이 비율만으로 정확하다.

나머지 6개 지표는 모두 `pose_world_landmarks`(3D)를 쓴다.

### 3.2 X-factor 신규 추가

어깨와 힙 회전의 차이로, 골프에서 비거리를 결정하는 핵심 지표다.
3D 좌표가 확보되면 추가 비용 없이 따라오는데 현재 지표 목록에는 없다.

### 3.3 체중 이동은 대리 지표로 강등한다

**영상만으로는 체중 이동을 측정할 수 없다.** 원래 정의(임팩트 시 앞발 체중 비율 %)는
압력판이 필요하다. 따라서:

- **이름**: `weight_transfer` → `weight_shift`
- **정의**: 골반 중심(23·24 중점) x좌표가 어드레스→임팩트 구간에서 타겟 방향으로
  이동한 거리를, 스탠스 폭(양 발목 간 거리) 대비 %로 표현
- **기준값**: 기존 `≥60%`는 다른 정의의 값이므로 폐기한다.
  **잠정 목표 10~20%**로 두고, §7 4단계의 실제 영상 검증에서 확정한다
- **표시**: 화면과 프롬프트 양쪽에 **"추정치"로 명시**한다

측정할 수 없는 것을 측정한 척한 것이 현재 문제의 출발점이다. 같은 실수를 반복하지 않는다.

### 3.4 절대 원칙 — 가짜 기본값 금지

> **측정에 실패한 지표는 기본값으로 채우지 않는다.**
> 랜드마크 visibility가 임계치 미만이거나 단계 탐지에 실패하면 해당 지표를 `None`으로 두고,
> 화면과 LLM 프롬프트 양쪽에서 **"측정 불가"로 표시**한다.

`metrics.get("hip_rotation", 32.0)` 패턴이 이번 문제의 직접적 원인이다.
없으면 없다고 말하는 쪽이 항상 낫다.

### 3.5 신뢰도 기록

단계 탐지 정확도가 모든 지표의 전제다. 어드레스/탑/임팩트 프레임이 틀리면 지표 전부가 틀린다.
이번 범위에서 단계 탐지 알고리즘은 건드리지 않되(§1 비목표),
각 지표에 **신뢰도 값을 함께 기록**해 의심스러운 경우 화면에 표시한다.

신뢰도는 해당 기준 프레임에서 계산에 사용된 랜드마크들의 `visibility` 최솟값으로 한다.

## 4. 모듈 구조

### 4.1 현재 상태의 문제

`backend/app/services/pose_estimator.py`는 **439줄에 8가지 책임**이 섞여 있다:
영상 다운로드, 모션 스캔, 포즈 추정, 7단계 탐지, 지표 계산, 오버레이 렌더,
R2 업로드, DB 기록. 지표 계산 로직을 여기에 더 얹으면 손댈 수 없는 파일이 된다.

### 4.2 목표 구조

```
backend/app/services/
├── swing/
│   ├── __init__.py
│   ├── phases.py     # 스윙 구간 탐지 + 7단계 분할
│   ├── pose.py       # YOLO 탐지 → ROI 크롭 → MediaPipe 3D 추출
│   ├── metrics.py    # 3D 좌표 → 지표 8개  ← 순수 함수
│   ├── overlay.py    # supervision 기반 렌더
│   └── pipeline.py   # 오케스트레이션 (DB·R2·asyncio)
└── feedback/
    ├── __init__.py
    ├── rules.py      # 지표 → 진단·점수 (규칙 테이블)
    ├── drills.py     # 진단 → 드릴 라이브러리
    └── llm.py        # Gemini 윤문. 실패 시 rules 결과 그대로 반환
```

각 모듈의 계약:

| 모듈 | 입력 | 출력 | 의존 |
|---|---|---|---|
| `phases.py` | 영상 경로 | 단계별 프레임 인덱스 + fps | cv2, numpy |
| `pose.py` | 영상 경로, 프레임 범위 | 프레임별 3D 랜드마크 + 2D 랜드마크 + 원본 프레임 | mediapipe, (ultralytics) |
| `metrics.py` | 3D 랜드마크 배열 + 2D 랜드마크 배열(§3.1), 단계 인덱스, fps, `camera_angle`(§9.5) | 지표 dict (값 + 신뢰도) | numpy만 |
| `overlay.py` | 프레임, 2D 랜드마크, 라벨 | JPEG bytes | supervision, cv2 |
| `pipeline.py` | `upload_id` | (DB 기록) | 위 전부 + DB + R2 |
| `rules.py` | 지표 dict | 진단·점수·등급 | 없음 |
| `drills.py` | 진단 목록 | 드릴 목록 | 없음 |
| `llm.py` | 규칙 결과 | 윤문된 결과 (실패 시 입력 그대로) | httpx |

**`metrics.py`가 순수 함수라는 점이 핵심이다.** 3D 좌표 배열이 들어가고 지표 dict가 나온다.
DB도 파일도 네트워크도 건드리지 않으므로 테스트가 쉽고,
지표의 정확성을 먼저 검증한 뒤 나머지를 붙일 수 있다.

### 4.3 규칙 엔진과 LLM의 관계 역전

| | 현재 | 변경 후 |
|---|---|---|
| 진단·점수·드릴 결정 | LLM | **`rules.py` / `drills.py`** |
| LLM의 역할 | 전부 | **한국어 문장 다듬기만** |
| LLM 실패 시 | 빈 껍데기 + "혼잡합니다" 메시지 | **규칙 결과가 그대로 나감** |

현재 `_calculate_score()`의 기준값들이 프롬프트 문자열에 하드코딩되어 있다.
이를 `rules.py`의 데이터 테이블로 옮긴다.

## 9. 기기 간 흐름 — 모바일 촬영 → PC 상세 분석

### 9.1 사용 시나리오

**두 기기를 동시에 쓰는 것이 아니다. 시간과 장소가 분리된다.**

```
야외(연습장)   폰으로 촬영 → 업로드 → 즉시 간단 코칭을 받고 바로 다음 스윙
      ⋮        (몇 시간 뒤, 집에 돌아와서)
PC            같은 계정 로그인 → 히스토리에서 오늘 스윙을 골라 → 상세 분석
```

PC에는 스윙을 찍을 카메라가 없고, 연습장에 PC를 들고 갈 수도 없다.
반대로 지표 8개와 7단계 오버레이를 제대로 뜯어보려면 화면이 넓어야 한다.
**현장 입력은 모바일, 사후 정밀 검토는 PC**라는 분업이다.

두 기기가 실시간으로 연결될 필요가 없으므로 **QR 페어링·세션 연결·폴링은 필요하지 않다.**
같은 계정으로 로그인해 있기만 하면 된다.
따라서 이 기능의 본체는 **§9.2의 `user_id` 귀속 버그 수정과 히스토리 복구**다.

### 9.2 선행 조건 — 살아 있는 버그

`POST /upload`은 **인증을 받지 않고 `user_id`를 설정하지 않는다.**

```python
db_upload = Upload(storage_url=storage_url, file_size=file_size)   # user_id 없음
db_analysis = Analysis(upload_id=db_upload.id, status="queued")    # user_id 없음
```

반면 `GET /history`는 `Analysis.user_id == uid`로 필터한다.
→ **`user_id`가 항상 `NULL`이므로 히스토리는 로그인해도 항상 빈 배열이다.**

기기 간 흐름은 "이 영상이 누구 것인가"를 서버가 알아야 성립하므로,
이 버그 수정이 선행 조건이다. 히스토리 복구는 덤으로 따라온다.

**변경**: `POST /upload`이 `Authorization: Bearer` 헤더를 **선택적으로** 받는다.
토큰이 있으면 `user_id`를 채우고, 없으면 기존처럼 익명 업로드로 남긴다
(`ANON_DAILY_LIMIT` 설계를 깨지 않기 위해).

### 9.3 히스토리 — PC의 주 진입점

PC 사용자는 방금 찍은 영상을 보러 오는 것이 아니라 **몇 시간 전에 찍어 둔 것을 찾으러** 온다.
따라서 `GET /history`가 PC의 첫 화면이 된다. 현재 이 화면은 §9.2의 버그로 항상 비어 있다.

**히스토리 목록 항목에 필요한 정보** (현재 반환값에서 확장):

| 필드 | 현재 | 변경 |
|---|---|---|
| `analysis_id`, `upload_id`, `status` | 있음 | 유지 |
| `overall_score`, `grade` | 있음 | 유지 |
| `thumbnail` | 있음 (임팩트 오버레이) | 유지 |
| `completed_at` | 있음 | 유지 |
| `camera_angle` | 없음 | **추가** — 목록에서 측면/정면을 구분해야 비교가 가능하다 |
| `measured_count` | 없음 | **추가** — 8개 중 몇 개가 실측됐는지. 촬영 실패한 영상을 목록에서 걸러낼 수 있다 |

**목록 UX 요구사항**:

- 날짜별로 묶는다. 연습장에서 한 번에 여러 스윙을 찍으므로 같은 날 항목이 여럿이다.
- 촬영 각도와 점수를 목록에서 바로 보여준다.
- `limit=20` 고정을 페이지네이션으로 바꾼다.

**새 테이블은 필요하지 않다.** `uploads`에 `camera_angle` 컬럼 1개만 추가하면 된다
(Alembic 리비전 1건).

### 9.4 모바일 촬영 화면과 야외 업로드

`NewUI/capture.html`과 `NewUI/mobile.html`에 프로토타입이 있으므로 디자인은 이를 따른다.

`AGENTS.md` 절대 규칙에 따라 **`getUserMedia` 호출은 반드시 try-catch로 감싸고**,
권한 거부·미지원·카메라 없음을 각각 구분해 한국어로 안내한다.
어느 경우든 **갤러리에서 파일 선택**이라는 대체 경로를 항상 함께 제시한다.
촬영이 불가능해도 업로드는 가능해야 한다.

#### 촬영 해상도·프레임율 정책

연습장 LTE에서 10~30MB를 올리는 것이 이 시나리오의 핵심 실패 지점이다.
**해상도를 낮춰 용량을 줄이되, 프레임율은 유지한다.** 골프 임팩트는 매우 빠른 동작이라
프레임을 줄이면 임팩트 순간을 놓친다.

```js
getUserMedia({ video: {
  width:     { ideal: 1280 },
  height:    { ideal: 720  },
  frameRate: { ideal: 60, min: 30 },
}})
```

720p를 고른 근거:

- **서버가 어차피 640p로 줄인다** (`PROC_W = 640`). 1080p로 올려도 그대로 버려진다.
- 그렇다고 640p로 찍으면 안 된다. **YOLO ROI 크롭(§2.2)이 골퍼 영역만 잘라내므로,
  골퍼가 화면의 1/3을 차지하면 크롭 후 해상도가 240p까지 떨어진다.**
  720p가 크롭을 감안한 하한선이다.

**갤러리에서 고른 영상은 원본 그대로 올린다.** 브라우저에서 재인코딩하면
폰에서 수 초~수십 초가 걸려 오히려 체감이 나빠진다. 기존 100MB 제한을 유지하고
진행률과 재시도 버튼으로 대응한다.

#### 서버 측 프레임 샘플링 재검토 — 필수

현재 `analyze_swing()`은 `SKIP = 2`로 **매 2번째 프레임만 분석하고 나머지를 버린다.**
클라이언트에서 60fps로 찍어도 서버에서 실질 30fps가 되므로 위 정책의 의도가 반감된다.

임팩트 구간만이라도 전 프레임을 쓰도록 **구간별 가변 샘플링**을 검토한다 —
어드레스~탑은 듬성듬성, 다운스윙~임팩트는 촘촘하게. §7 4단계의 통합 검증에서
프레임율이 지표 정확도에 실제로 얼마나 영향을 주는지 측정한 뒤 값을 확정한다.

#### 발견된 문서·코드 불일치

`docs/04_roadmap_7days.md`가 완료로 표시한 항목 중 코드와 어긋나는 것이 있다.
§5 문서 갱신 시 함께 바로잡는다.

| 로드맵 기재 | 실제 코드 |
|---|---|
| "6프레임 스킵 (기존 3프레임 → 2배 추가 단축)" | `SKIP = 2` |
| "최대 150프레임 처리 후 조기 종료" | 해당 로직이 존재하지 않음 |

### 9.5 촬영 각도 선택 — §6 최상위 리스크의 근본 대응

촬영 각도를 모르면 회전 지표가 쓰레기가 된다. 촬영 직전에 사용자가 고르게 한다.

| 각도 | 설명 | 신뢰할 수 있는 지표 |
|---|---|---|
| `down_the_line` | 타겟 방향으로 서서 뒤에서 촬영 | 척추 각도, 무릎 굴곡, 어깨/힙 회전, X-factor |
| `face_on` | 정면에서 촬영 | 헤드 무브먼트, 체중 이동, 템포, 무릎 굴곡 |

`metrics.py`는 `camera_angle`을 입력으로 받아 **해당 각도에서 신뢰할 수 없는 지표를
`None`으로 반환**한다 (§3.4 원칙과 동일). 화면에는 "이 각도에서는 측정할 수 없음"으로
표시하고, 다른 각도로 한 번 더 촬영하도록 안내한다.

이것이 §6의 "정면 촬영 시 어깨 회전 불안정" 리스크에 대한 근본 대응이다.
신뢰도 표시로 얼버무리는 대신, 애초에 계산하지 않는다.

### 9.6 뷰 분기 — 같은 데이터, 다른 깊이

**분석은 기기와 무관하게 한 번만 돌린다.** 서버는 항상 전체 결과를 반환하고,
프론트엔드가 어느 만큼 보여줄지 고른다. 이유는 두 가지다 —
서버 CPU를 두 배로 쓰지 않기 위해서, 그리고 **두 화면의 숫자가 어긋나는 사고를 막기 위해서**다.
따라서 뷰 분기용 API는 추가하지 않는다.

| 항목 | 모바일 요약 | PC 상세 |
|---|---|---|
| 종합 점수·등급 | ✓ | ✓ |
| 최우선 이슈 | 1개 | 3개 + 상세 피드백 |
| 드릴 | 1개 | 전체 |
| 오버레이 | 임팩트 1장 | 7단계 전부 |
| 지표 | 상위 3개 | 8개 전체 + 기준 대비 게이지 |
| 과거 비교 / 추이 | ✗ | ✓ (`/compare`, `/progress`) |

PC 사용자는 히스토리(§9.3)를 거쳐 들어오므로, 상세 화면에는
**같은 날 찍은 다른 스윙으로 바로 넘어가는 경로**가 있어야 한다.

모바일 요약 화면 하단에는 **"집에서 PC로 자세히 보기"** 안내를 둔다.
현장에서는 다음 스윙을 치는 것이 우선이므로, 요약 화면은 스크롤 없이 한 화면에 끝나야 한다.

**뷰 선택 방식**: 화면 폭으로 기본값을 정하되 **강제하지 않는다.**
"상세 보기" / "간단히 보기" 토글을 두어 사용자가 언제든 바꿀 수 있게 한다.
PC에서 창을 좁게 띄웠다는 이유로 요약만 보이면 안 된다.
